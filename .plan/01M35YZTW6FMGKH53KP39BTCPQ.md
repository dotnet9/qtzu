## 〇、先更正上一轮的一个错误结论（重要）

我在对话里曾说"烘焙数据缺了男孩下半身"——**这是错的**，查证后推翻：

| 部件 | 源（程序化，相对自身） | 烘焙 GLB（`assets/models/manifest.json`） |
|---|---|---|
| `p-boy-body` | y **0.18 ~ 0.49** | y **0.18 ~ 0.49** ✓ 完全一致 |
| `p-boy-legL` | y −0.25 ~ 0.06 | y −0.321 ~ −0.018 |
| `p-girl-body` | y 0.014 ~ 0.455 | y 0.014 ~ 0.455 ✓ |

`p-boy-body` 的 7 个图元（胯部柱/腰带/上衣球/两条背带/前口袋/口袋口）一个不少。所以**不是烘丢了，是造型本身有缺口**：

- 胯部柱 `cyl(body, 0.15, 0.165, 0.12, …)` 中心 0.24 → 占 y **0.18 ~ 0.30**
- 上衣球 `sph(body, 0.128, …)` 中心 0.41、y 缩放 0.55 → 占 y **0.34 ~ 0.48**
- 中间 **0.30 ~ 0.34 只有两条 6cm 宽的背带连着** → 俯视能直接看穿（这就是"身体是空的"）
- 叠上草帽檐半径 0.26（比头半径 0.185 宽 40%），俯视 = "一顶大帽子 + 两条腿"

另有两个"看起来不一样"的原因（不是 bug，是两条渲染路径的差异）：

- 选择卡：`playerThumbnail()` → **程序化模型** + 三点光（key 2.6 / fill 0.95 / rim 1.7）+ PMREM 环境 + 接触阴影 + 俯视 3/4 机位（`js/models/build.js:97-130`）
- 游戏内：先程序化、再被 `assets.applyParts()` **逐部件换成烘焙 GLB**（`js/game.js:389`），GLB 还要过 `js/assets.js:131-135` 的强制哑光化（`roughness≥0.82 / metalness 0 / envMapIntensity 0.7`），光照只有 hemi 0.62 + sun 1.35 且**相机远、有雾**

用户四项选择（已定）：**保留烘焙把 GLB 修对** / **补腰腹缺口 + 草帽檐缩小加厚 + 顺便加细节** / **缩略图与游戏内两边向中间靠** / **跳跃引导全做（含失败提醒）**。

### 1.4 重烘 GLB（用户选择"保留烘焙，把 GLB 修对"）

按既有管线（`.cache/bake-player6.log` 记录过完整序列），**5 步**：

1. `node scripts/extract-prims.mjs --kind player` → `.cache/bake/prims.player.json`（24 变体、每格带 `bbox` = 源局部包围盒）
2. Blender 执行既有烘焙脚本 `scripts/bake/pets.py`（**先 `--limit 2` 试跑**确认参数名/输出路径，再全量）：
   `E:\tools\blender-4.5.14-windows-x64\blender.exe -b -P scripts/bake/pets.py -- --specs <prims.player.json 或包装后> --out assets/models --manifest .cache/player.manifest.json`
3. `node scripts/bake/merge-part.mjs player` → 合并进 `assets/models/manifest.json`（自动补 `v` 内容哈希 → 长缓存自动失效，不会拿到旧模型）
4. 若 key 集合变化产生多余旧 GLB：`node scripts/bake/prune-manifest.mjs`
5. `node scripts/audit-assets.mjs` → 必须 **0 缺失 / 0 孤儿 / 0 超预算**，且"最低点与源差 ≤0.02"逐格通过

> 注：`scripts/bake/run.mjs` 的 `BAKERS` 里**没有 player**（只有 gate/landmark/ground），所以这条是独立管线（`.cache/player.manifest.json` + `merge-part.mjs`）。步骤 2 的 `--specs` 形式以试跑实测为准，计划不写死。

## 二、缩略图 ↔ 游戏内"两边向中间靠"

### 2.1 缩略图侧（`js/models/build.js`）

- 相机：`(cx + maxDim*0.7, cy + maxDim*0.42, cz + maxDim*1.5)` → `(cx + maxDim*0.45, cy + maxDim*0.24, cz + maxDim*1.7)`，**俯角约 22° → 13°**（向游戏内常规俯角靠，不再"从头顶拍"）
- 主角专用打光（`litScene` 加 `opts.player` 分支）：key 2.6→2.2、fill 0.95→**1.15**、rim 1.7→1.35；接触阴影 `opacity 0.75→0.5`、半径系数 `0.52→0.46`（"影棚感"保留，但不再像悬空贴片）
- 词宠缩略图**不动**（用户上轮明确只做强主角）

### 2.2 游戏内侧（`js/world.js` + `js/game.js`）

- `world.js:742-761` 的 `hemi` / `sun` 挂进 `world.anim.lights = { hemi, sun }`
- `game.js` 新增 `_setupPlayerFill()`：两盏 `DirectionalLight`（fill 0.5 / rim 0.75，`castShadow = false`），每帧位置 = 玩家位置 + 相机方向偏移（肩后上方 + 逆光侧）
- 同时把 `hemi` / `sun` 强度乘 **0.88 / 0.92**（补光顶上来的总量，避免整体过曝）
- 降级：`isTouch` 或 `_lowFx` 时不加灯、不调强度（与 SMAA/环境反射同一判据）
- 代价：+2 draw call 的光照计算（无阴影贴图，几乎不影响帧时长）

## 三、跳跃玩法"看得懂"（含失败提醒）

现状（`js/world.js:1707-1777`）：观景石台顶面高出地形 **3.45**，3~5 级台阶水平退 **1.7**、抬高 **1.35**、半径仅 **0.85**（比角色步幅还窄），且**没有任何一处告诉玩家要跳**（`js/ui.js:3016` 的帮助里也没写）。

### 3.1 地形与标识（`js/world.js`）

- 石阶半径 **0.85 → 1.4**（碰撞 `colTop` 同步 1.4）；云梯 `PROPS.cloud(1.15) → PROPS.cloud(1.5)`，平台半径 **1.35 → 1.6**
- 水平间距 **1.7 → 1.25**（`dPerch - k*1.25`），垂直降幅 **1.35 保持**（力学不变：单跳 1.85 / 二段跳 3.30）
- 保证**至少 3 级**：不足 3 级时把石台顶面从 3.45 降到 2.85 并重算（"跳 3 下上去"的体验）
- 每级加**发光序号 Sprite**：第 k 级上方 `(sx2, want + 0.9, sz2)`，`letterTexture(String(k), 色, 底)`，`scale 0.5`；1 级金 `#F0C44E`、2 级薄荷 `#5BC79A`、3 级紫 `#B28FF5`
- 台顶加一圈**脉动发光环**（细 Torus）提示"这里是终点"

### 3.2 引导与反馈（`js/game.js`）

| 机制 | 触发 | 表现 |

## 五、风险与回退

- **重烘是风险最高的一步**（Blender 脚本参数靠试跑确认）。回退：`git checkout assets/models` 复原 50 个 GLB 与 manifest。
- 造型改动会让 `p-boy-*` / `p-girl-*` 全部换哈希 → `?v=` 机制自动失效长缓存，**无脏缓存风险**。
- 灯光分层若让 `check-render` 越界：先把 fill/rim 强度降 30%，仍越界则只在非触屏保留 fill（去掉 rim）。
- 台阶"至少 3 级"若与 `verify-jump.mjs` 的逐级上升冲突：以校验器为准，把石台顶面降到 2.85 而不是加级。

## 六、明确不做

- 不重烘 358 个词宠（用户上轮已定：只做强主角）
- 不改女孩裙子造型（只加鞋底白边 + 发丝）
- 不做"正式跳跃小关"（计时 / 星级评价）——留给下一轮
