## 二、关键做法：用"提取图元"代替"移植造型代码"

词宠造型在 `js/models/auto-templates.js`（47KB 参数化）+ `pets-shapes.js`，玩家在 `player.js`，
NPC 在 `npcs.js`。**手工移植到 Python 必然与 JS 分叉**（对方方案 §七 的担忧）。

本轮改成：`scripts/extract-prims.mjs` 在浏览器里用**真实 three** 把程序化模型提取成"图元清单"
（类型 + 参数 + 材质色 + 局部矩阵 + 源包围盒），JS 永远是唯一规则源；
Blender 只做风格化加工（顶点色 AO + 按角度拆边），与 gates/landmarks/ground 同一条管线。

## 三、本轮修掉的 bug（都在代码注释里留了记录）

1. **BUDGET 表混着两套声明**：字典式（`{'pet': {'tri': 6000}}`）与整数式（`'pet': 3500`）并存，
   后者覆盖前者，而 `check_budget` 只认整数 → 统一为整数并调上限（pet 8000 / player 12000 / npc 6000）。
2. **词宠细分过高**：原造型球是 18×14，图元化后单个 5974 面 → 降到 12×9（均值 2055 面）。
   依据：同屏最多 6 个词宠（`js/game.js` 的 `slice(-6)`），0.55 缩放下看不出差别。
3. **文件名带 `:`**：Windows 把 `boy:legL.glb` 当成 ADS 数据流，58 个只落盘 8 个 → 文件名用 `-`，逻辑 key 保留 `:`。
4. **NaN 图元**：造型里有位置/缩放算成 NaN 的退化件（游戏里本就不可见），提取时丢掉并记数。
5. **环面半径搞反**：three 的 `TorusGeometry` 是 `{radius, tube}`，提取时写反会把环建成一团。
6. **审计的"穿地"规则对词宠太严**：实测**原始 JS 模型本身就沉 ~0.075**（`degree` 的 `jsMinY = -0.0752`，
   与烘焙 GLB 完全一致 → 烘焙忠实于源）。改成"与源包围盒对账"（容差 0.02），比拍一个固定容差强得多。
7. **路灯灯泡自发光过高**：0.55 时灯头越过辉光门槛，`check-render` 的 `composerDiff` 被顶到 0.037
   （门槛 0.02）→ 降到 0.28（辉光预算留给蛋/词宠这些真正的发光物，与校门石灯同样处理）。
