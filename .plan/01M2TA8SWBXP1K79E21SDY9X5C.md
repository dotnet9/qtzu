# 3D 地图全量改造：52 城真实地貌 + 立体全国地图 + 地形玩法

## 一、目标与验收

把"成都勉强还行、其他城市差很多"变成**52 城各有辨识度**：山在正确方位、大河走向对得上、湖/海岸在正确角落；装饰与地标贴合地形；配色按气候带分化；拉远的全国地图也能看到邻城的地形浮雕；每城有一个地形打卡点，地形本身影响移动手感。

**验收（可量化，全部要跑）**
1. `node scripts/verify-terrain.mjs` → 52 城 0 报错、0 控制台错误。
2. 新增 `node scripts/audit-terrain.mjs` → 每城报告：地标真实高度、河湖是否落在轮廓内、地形起伏率（非零高度采样点占比）。**硬门槛**：52 城起伏率 ≥ 40%；有山城市的主峰实高 ≥ 4m；湖/河控制点 100% 在轮廓内。
3. 截图对比（`scripts/tpl-shots.mjs` 扩展到 12 城）：同分区模板的城市两两截图**肉眼可分辨**。
4. 每城能从广场步行到地形打卡点，沿途单步高差 < 2m（不卡台阶）。
5. 拉远全国地图，邻城可见地形浮雕；帧率不低于改造前（同机同镜头对比）。

## 二、现状诊断（已逐行核实）

### 2.1 地形是数据驱动的，但只有 3 城是手调的
- `js/terrain.js` 是通用引擎：`createCityTerrain({pts, cfg})` → `{group, heightAtLocal}`；`js/world.js:1016` 挂载；`js/game.js:2609 _groundY` 供玩家/NPC/词宠寻高。
- 52 城**都有** `data/cities/<id>/terrain.json`（`js/data.js:69` 可选加载，缺文件走平地）。但只有 `chengdu` / `zhengzhou` / `zhuhai` 是手调的，其余 49 城是 `scripts/gen-terrain.mjs`（71 行）用**15 个分区模板**批量套出来的。

### 2.2 根因 A：模板只有 15 个，同模板城市地形完全一样
`scripts/gen-terrain.mjs:31-46` 的 15 个模板 + `:47-62` 的分配表：
- **9 城共用 `imperial`**：beijing / tianjin / shijiazhuang / zhengzhou / hefei / changchun / shenyang / kaifeng / qufu。
- **11 城共用 `coast`**：dalian / qingdao / xiamen / shenzhen / zhuhai / kaohsiung / taichung / tainan / taipei / fuzhou / quanzhou。

`base(id)`（`:20`）里唯一的城市差异是 `seed: hash(id)`，而 **`seed` 只喂给雪峰**：`js/terrain.js:25` 建 `rng`，只在 `:212`（雪峰顶点抖动）和 `:218`（雪峰旋转）用到。imperial / coast 模板都没有 `peaks` → **seed 完全没起作用**。于是北京和开封是同一座山丘、同一条河、同一片农田、同一套配色。

### 2.3 根因 B：没有山的城市高度恒为 0（噪声被关在山里）
`js/terrain.js:69-83`：

```js
const hRaw = (x, z) => {
  let h = 0;
  if (MNT) {                       // ← 噪声只在这个分支里加
    ...
    h += n2(x, z) * (noiseAmp + 1.05 * mM);
  }
  if (HIL) { ... }
  ...
};
```

没有 `mountain` 的模板（imperial / water / canal / coast / rivercity / ice / tropical / gardenhill 共约 30 城）→ `h` 恒为 0 → `quant()` 后全是 0 → **一片死平的绿板**，连台地纹理都没有。

### 2.4 根因 C：归一化只用一个 R，长短轴不区分
`js/terrain.js:17-22`：

```js
const W = maxX - minX, H = maxZ - minZ;
const R = W / 2;                 // x/z 共用同一个缩放
const N = (v) => v * R;
const P2 = (p) => [N(p[0]), N(p[1])];
```

而轮廓数据是**按最长半轴归一**的（`scripts/gen-city-shapes.mjs:103-110`）：`half = max(x 半跨, z 半跨)`，两个方向都除以 `half`。所以 `CITY_SHAPES` 里**长轴恰好铺满 [-1,1]，短轴只有 [-k,k]（k<1）**。

配置里 `z=-0.7` 的河、`z=-0.58` 的丘，在短轴方向被映射到 `-0.7R / -0.58R`，而轮廓在 z 方向只到 `kR` → **地物落在轮廓外**，浮在海面上；即使勉强落在轮廓内，也会撞上 `edgeFlat`（`:81`，靠边 3~10 米把高度乘到 0）被压平。

这就是"其他城市差很多"最直接的原因：**山被压平、河漂到海里**。

### 2.5 根因 D：广场压平半径过大
`scripts/gen-terrain.mjs:22`：`plaza: { center:[0,0.04], inner:0.10, outer:0.32, flat:0.9 }`。
`outer=0.32` × `R≈80` ≈ **25.6 米半径内高度压掉 90%**，而 `js/terrain.js:62` 用 `N(cfg.plaza.outer)` 换算。模板又把山/丘放在 `[-0.55,-0.42]` 一带（距中心约 0.69 归一 = 55m），一旦城市短轴小、`N()` 换算后落进 25 米内，山就没了。

### 2.6 成都为什么"勉强还行"
`js/world.js:1345` `if (isl.key === 'chengdu' && isl.shape)` → **只有成都**有悬浮岛（岩裙侧壁 + 底部垂石 + 环岛云海 + 云上暗影）；`js/world.js:205` → **只有成都**用专属贴图 `chengduTexture()`。其他 51 城是普通岛 + 通用草地贴图。

### 2.7 已经做对的部分（不要动）
- 装饰贴地链路是通的：`js/world.js:996` 的 `Y(x,z,base)` 已用在主地标（`:1317`）、观景石台（`:1412-1414`）、特产 emoji（`:1423`）、专属装饰（`:1433`）、花丛（`:1442`）、绿化树（`:1487`）、高楼（`:1502`）、许愿井/任务板（`:1555/1557`）；`js/game.js` 的校门（`:2065`）、探索立牌（`:2083`）、牌旁蛋（`:385`）、机关蛋（`:2576`）、玩家/NPC/词宠寻高（`:318/340/2599`）也都走 `_groundY`。
- 城墙/垛口/烽火台/岩裙/浪花用 `y=0` 硬编码是**正确**的：它们在轮廓边界上，而 `edgeFlat` 保证边界附近恒为 0。
- `js/city-shape.js` 提供 `polyInside` / `polyNearest` / `polyOffsetRing` / `polyPole`（内极点，凹形城市找城心用）/ `simplifyPoly` / `clampPoly`，全是现成的共享几何工具，新代码一律复用，不要再写一份。

### 2.8 全国地图现状
`js/china-map.js:82-152`：按 `CITY_GEO` 真实经纬度平铺 `CITY_SHAPES` 的 **2D 平面**（投影暗影 + 状态晕圈 + 渐变填充 + 双线描边），比例 `UPD=420` 世界单位/度、`LAT_K=cos35°`、底图 `BASE_Y=-2`。**没有任何高度**。

### 2.9 轮廓数据现状
`js/city-shape-data.js` 的 `CITY_SHAPES` 覆盖 **48 城**（`scripts/gen-city-shapes.mjs:16-30` 的 52 个 adcode 里，台湾 4 城 DataV 返回 404 → 未收录）；台湾 4 城（taipei / kaohsiung / taichung / tainan）走 `js/city-shape.js:22-27` 的 `TW_SHAPES` 示意轮廓。`js/city-shape.js:8-19` 另有 10 城简笔 `SHAPES` 作为兜底。所有 `city.json` 的 `level.shape` 都是 `null`（已抽查 changchun/lanzhou/chengdu），即全部走 `getCityShape()` 的优先级链：`level.shape → CITY_SHAPES → SHAPES → TW_SHAPES → blob`。

## 三、改造设计

### 阶段 0：打通坐标口径（其余一切的前提）

**改 `js/terrain.js:17-22`**，把单一 `R` 换成双轴 + 包围盒中心：

```js
const W = maxX - minX, H = maxZ - minZ;
const RX = W / 2, RZ = H / 2;
const CX = (minX + maxX) / 2, CZ = (minZ + maxZ) / 2;   // 轮廓归一化本就以包围盒为中心，这里补齐
const N  = (v) => v * RX;                                // 长度/半径：按横向半跨换算
const P2 = (p) => [CX + p[0] * RX, CZ + p[1] * RZ];      // 点：两轴各自映射
```

- 所有 `N(...)` 长度类参数（`near/far/ridge.w/plaza.*/terrace.rx/farm.r0,r1/colorCell` 之外的）语义不变，只是横向基准从 `W/2` 明确为 `RX`（原本就是同一个值）。
- 需要单独改的**两个**地方：`js/terrain.js:88` 的 `TER.rz` 改用 `RZ`；`:204` 雪峰坐标改用 `P2(def)`（目前是 `N(def[0]), N(def[1])`）。
- **兼容性**：因为 `city-shape-data.js` 已按包围盒居中（`gen-city-shapes.mjs:103`），且 `CX≈0`，所以 `CX` 的引入对 48 个真实轮廓城市**几乎无位移**；`RZ` 才是真正的行为变化。
- **成都迁移**：成都也是按同一规则归一的数据，迁移公式 `z_new = z_old × (sx/sz)`，`x` 不变；`terrace.rz` 同乘。写进生成器的一次性 `--migrate-chengdu` 模式里，跑完人工确认成都外观与改造前一致（截图 diff）。

### 阶段 3：地标与装饰贴地、广场避让

1. **广场避让**：生成器在自动贴合阶段，把山/丘中心从 `plaza.outer` 半径内推出去（朝轮廓内极点方向，用 `polyPole` 同款算法），避免"出生台把山压平"。
2. **装饰贴地补齐**：`js/world.js:1153-1193` 沿墙两排树用 `y=0` 硬编码 —— 这些在边界上（`edgeFlat` 内恒为 0），**不改**。需要补的是任何"按半径撒但落在城内深处"的装饰；逐个核对 `js/world.js:1410-1508`，凡已有 `Y()` 的不动，缺的补上。
3. **地标朝向与地形**：主地标/观景石台已在 `:1317/:1412` 贴地；补一条"石台高度 = `_groundY`"的一致性检查（`js/game.js:1857` 的天空蛋位与 `js/world.js:1410` 的 `perchA/perchD` 必须同参，已有注释约束，用脚本校验）。

### 阶段 4：地形影响移动（`js/game.js`）

| 效果 | 规则 | 落点 |

| 山上视野更远 | `camDist` 随脚下高度增加（每米 +0.6，上限 +18） | `_supportAt` 之后 |

### 阶段 5：地形打卡点（每城一个）

- **数据**：在 `terrain.json` 里加 `spot: { name, kind, at, r, stars }`（`kind` ∈ `summit/lakeside/dune/terrace/coast/river`），由生成器按地物自动推导（有山→`summit` 取主峰；有湖→`lakeside`；沙色→`dune`；有梯田→`terrace`；有海→`coast`；否则→`river`）。
- **表现**：复用 `js/game.js:_makeSign`（`:2100`）的立牌造型，加一个金色边框与 `kind` emoji；`at` 用 `clampPoly` 钳进城内并贴地。
- **交互**：走近（半径 `r`）自动盖章 +⭐，弹一次 toast（复用 `ui.toast`），已盖章存进 `save`（新增 `save.getSpots()/markSpot(cityId, kind)`，与 `js/save.js` 现有 profile 字段风格一致）。

### 阶段 6：悬浮岛待遇推广到 52 城

`js/world.js:1345` 现在写死 `isl.key === 'chengdu'`，`js/world.js:205` 写死成都专属贴图。改法：

### 阶段 7：全国地图立体化

`js/china-map.js:82-152` 的 2D 平铺改为 **2.5D 浮雕**：

2. 全国地图里每城用 `buildTerrainMesh(..., cheap)`，网格按 `s = CITY_GEO.halfDeg * UPD` 缩放后放到 `BASE_Y` 之上；高度按 `CITY_GEO.halfDeg` 做一次统一压缩（保证 52 城相对高低可比，且不遮住城市名牌）。
3. **性能闸门**：预算 `52 城 × ≤ 6k 顶点`；超出则按"离镜头距离 + 是否已攻克"分级降级（远处只留描边+填充）。实测帧率不低于改造前。

### 阶段 8：轮廓增强（可选，放最后）

目标：让城廓更像真城市（圆滚滚的 blob 与过度简化的边界）。做法：`scripts/gen-city-shapes.mjs` 的简化容差从 `diag*0.0002` 收到 `diag*0.00008`，并把点数上限从 3600 提到 6000；跑完必须重跑 `scripts/check-city-neck.mjs`（窄颈连通性）与 `scripts/check-city-boundary.mjs`（元素越界）。

## 六、边界情况与风险

1. **成都回归**：坐标口径变更会影响成都。迁移用 `z_new = z_old × (sx/sz)`，先截图 diff 再继续；若观感变化明显，接受"成都也变好"但要在提交信息里写清。
2. **旧存档**：地形配置不参与存档，玩家位置在换城时由 `_citySpawnPos` 重算 → **无需迁移**。新增的打卡点数据是新字段，老存档读不到时按空集处理（`js/save.js` 现有 `merge` 逻辑风格）。
3. **窄颈城市**：兰州/无锡这类凹形轮廓，`polyPole` 的内极点可能落在凹口外 —— 贴合时若"最深处"点集为空，退回包围盒中心并在报告里标记。
4. **地物全部贴边**：某条山脉若整条都在 `edgeFlat` 带内，宁可**删掉它**并在生成报告里写"删 X 条（贴边立不起来）"，也不要在配置里留一个上岛看不见的山。
5. **性能**：阶段 7 的 52 城粗模是最大风险，必须有预算闸门与分级降级；阶段 8 若不达标整段回退。
6. **不做的事**：不改 `step`/`flatShading`（手办风是既有美术方向）；不重写 `city-shape.js`；不动 `edgeFlat`（依赖它的摆放/碰撞逻辑很多）；不做真实地形高程数据接入（用"地标方位 + 走向"的示意，够孩子认得出即可）。
